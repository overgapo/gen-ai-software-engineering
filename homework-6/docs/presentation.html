Transaction Processing Pipeline

A four-stage payment pipeline built end to end by four AI workflow agents — specification, code, tests, documentation — where every decision stays explainable after the fact.

1
The problem

Money code fails quietly

The defects that matter here look, in a diff, exactly like ordinary working code.

  • A float where a Decimal belonged — off by a cent, found at reconciliation weeks later.
  • An account number in a log line — invisible until an audit.
  • A filing treated as a hold — a compliance obligation quietly turned into a blocked payment.
  • A guessed FX rate when the real one was missing — plausible, wrong, and unreviewable.
So the design goal was not "make it work". It was: make every outcome reconstructable by hand, months later.

Decision rules

Closed sets, not "e.g."

Validation — 10 checks, first failure wins

MISSING_FIELD · INVALID_TIMESTAMP · INVALID_ACCOUNT_FORMAT · SAME_ACCOUNT · UNSUPPORTED_CURRENCY · MALFORMED_AMOUNT · NON_POSITIVE_AMOUNT · AMOUNT_SCALE_MISMATCH · AMOUNT_OUT_OF_RANGE · UNSUPPORTED_TRANSACTION_TYPE

Scale follows the ISO 4217 exponent — 2 for USD, 0 for JPY. "1000.5" JPY is malformed input, not a value to round.

Fraud — additive, capped at 100

HIGH_VALUE ≥ 10 00040
VERY_HIGH_VALUE ≥ 50 00020
STRUCTURING [9 000, 10 000)25
UNUSUAL_HOUR 00:00–04:59 UTC20
CROSS_BORDER15
UNATTENDED_CHANNEL (api)10

LOW 0–24 · MEDIUM 25–59 · HIGH ≥ 60 → held. A score never travels without the signals that produced it.

MCP integration

Two servers: one consumed, one built

context7 — consumed during code generation

Three queries, documented in research-notes.md with library IDs and what each one changed.

The useful one corrected code I had already written. POST /api/run used Starlette's run_in_threadpool from an async def — hand-rolling what FastAPI does from the signature. The docs' idiom is a plain def path operation. One dependency dropped out of the file.

pipeline-status — built with FastMCP

get_transaction_status(id) · list_pipeline_results() · resource pipeline://summary

Read-only and stateless: stdio spawns a fresh process per session, so every call reads shared/results/ from disk and can never serve a stale answer after a new run.

Returns the same projection the dashboard uses — account numbers and descriptions never leave the server.

8
Lessons learned

What the process actually taught

  • The spec paid for itself at the §9 table. Assigning every one of the 8 sample records a defined outcome before coding turned the integration test into a transcription job — and caught that a "compliance" stage with nothing to decide is untestable theatre.
  • Freeze the spec, then amend it deliberately. Two implementation decisions drifted from the document; both were written back into it in the same commit. Silent drift is how a spec stops being trustworthy.
  • Verify by breaking, not by reading. The coverage gate only became evidence once it actually blocked a push twice.
  • Documentation lookup beats recall. context7 found a real mistake in code that already worked — the kind that passes tests and reviews.
  • Tests for absence are the ones that hold. "No float in the money path" survives a refactor by a developer who never read the spec; a comment does not.
  • Two debugging traps worth remembering: an MCP stdio client that pipes every request at once gets cut off at EOF; and a same-length edit with an older mtime leaves a stale .pyc that fails a test you already fixed.
