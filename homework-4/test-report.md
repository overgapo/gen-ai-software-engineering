## FIRST Compliance

- **Fast** — All 14 tests run in-process via `supertest(createApp())`; no `app.listen()`,
  no network I/O, no real timers or sleeps. Full suite runs in 0.744s.
- **Independent** — `beforeEach` calls `store.reset(SEED)` (or `store.reset([])` for the
  validation block) before every test, so no test observes another's writes (POSTs,
  DELETEs). The security block additionally calls `jest.resetModules()` per test via
  `freshAppWithKey()` so each test gets its own module instance with its own captured
  `API_KEY` — required because `src/expenses.js` reads `API_KEY` into a module-level
  constant at `require` time, so no test's env mutation leaks into another's app instance.
  `afterEach` restores the original `API_KEY` and resets modules again.
- **Repeatable** — All dates are fixed literals (`2026-01-05`, `2026-01-31`, `2026-02-01`,
  etc.), never `Date.now()` or `new Date()`. The one env-var dependency (`API_KEY`) is set
  deterministically inside each test via `freshAppWithKey()` and restored in `afterEach`,
  so the suite is unaffected by whatever `API_KEY` is set in the ambient shell.
- **Self-validating** — Every test asserts concrete expected values
  (`expect(summary.body.total).toBe(20.75)`, `expect(res.status).toBe(401)`,
  `expect(freshStore.getById(1)).toBeUndefined()`) — no `console.log`-and-eyeball, no test
  without a hard assertion.
- **Timely** — Every test targets exactly one of the four changes listed in
  `fix-summary.md`; nothing tests unrelated routes (`GET /expenses/:id`, `POST` happy path
  beyond what validation needs) that the Fixer didn't touch.

## Boundary Cases Covered

- **Date-range boundary:** a record dated exactly on the `to` value (`2026-01-31`) — the
  exact edge the `<` vs `<=` bug lived on — asserted present in both `/expenses` and
  `/summary`.
- **Filtered vs. unfiltered summary:** asserted the filtered total both **equals** the
  correct aggregate and **differs** from the unfiltered total, so a fix that only partially
  applies the filter (e.g. to `count` but not `total`) would still be caught.
- **Floating-point boundary:** four distinct two-decimal values known to hit IEEE-754
  rounding error under `n * 100` (`8.29`, `19.99`, `0.07`, `12.5`) are asserted accepted,
  and `1.005` (three decimal places) is asserted still rejected — covering both sides of
  the `hasAtMostTwoDecimals` boundary.
- **Auth fail-closed boundary:** in addition to correct-key/wrong-key, the missing-header
  and unset-`API_KEY` cases are asserted to fail closed (401), which is the specific
  failure mode a naive secret-from-env fix could get backwards (e.g. treating an unset
  key as "no restriction").
